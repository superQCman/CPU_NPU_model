# DLRM 分层存储 — 基本原理

## 一、三级存储 (dlrm_msprof_mtrain.py)

### 1.1 核心思路

推荐系统中 Embedding Table 往往极大（百万～十亿行），远超单卡 NPU HBM 容量。MTrainS 的核心思想是按访问热度将 Embedding 分层存储：热点放 HBM（NPU 显存）、温数据缓存在 DRAM（CPU 内存）、冷数据存在 SSD，按需逐级加载。

### 1.2 存储层级

| 层级 | 介质 | 容量 | 实现 |
|------|------|------|------|
| Level 0: HBM | NPU 显存 | `num_embeddings × hbm_ratio`（默认 1%） | `nn.Parameter`，参与梯度更新 |
| Level 1: DRAM | CPU 内存 | `num_embeddings × dram_cache_ratio`（默认 5%） | 热度管理字典 `dram_data`（指数衰减热度阈值，取代 LRU）|
| Level 2: SSD | 持久化磁盘 | 全量 | `SSDStorage`，`np.memmap` 稀疏文件（`embedding_table.bin`）|

各层级容量占比通过命令行参数手动配置。

### 1.3 查找流程

```
forward(indices)
  │
  ├─ torch.isin(indices, hbm_indices)  → HBM 命中？
  │   └─ Yes: hbm_weight[searchsorted(pos)] 向量化 gather（NPU 片上读）
  │
  ├─ dram_data.get(idx)  → DRAM 命中？
  │   └─ Yes: torch.stack(vecs).to(device) 批量 CPU→NPU
  │
  └─ ssd_storage.get_row(idx)  → SSD 冷加载
      └─ 读 memmap 一行 + .to(device)（不回填 DRAM，由迁移统一预取）
```

关键设计：HBM 通过 `hbm_indices` 动态维护当前 HBM 中存的是哪些逻辑索引，用 `torch.isin` + `torch.searchsorted` 实现向量化查找。

### 1.4 冷热迁移（热度阈值驱动）

每次 forward 后触发一次 `_tier_migration`，热度用**指数衰减 + 访问累加**维护（`gamma=0.9`）：

```
_update_heat:  heat[e] = heat[e]·gamma；访问到的 e 再 heat[e] += 1
_tier_migration:
  1. 淘汰 HBM→DRAM: heat < tau_high 的行
  2. 淘汰 DRAM→SSD: heat < tau_low 的行（丢弃缓存副本）
  3. 预取 SSD→DRAM: heat ≥ tau_low 且不在 HBM/DRAM 的行
  4. 预取 DRAM→HBM: heat ≥ tau_high 的行（逐级晋升，不越级）
  5. HBM/DRAM 容量约束: 超出容量淘汰最冷行
  6. 重建 HBM（DRAM→HBM 的 host→device 拷贝发生在此）
```

迁移是**逐级**的（HBM↔DRAM↔SSD，不越级），后台执行，各链路分开计时。

### 1.5 访存计时

forward 内对 4 段数据通路分别计时，自动打印：

| 计时段 | 测量内容 |
|--------|---------|
| HBM → NPU | hit发生在HBM上的数据传输时间 |
| DRAM → CPU | hit发生在DRAM上的数据传输时间 |
| SSD → DRAM | 数据从SSD迁移到DRAM耗时 |
| DRAM → HBM | 数据从DRAM迁移到HBM耗时 |

## 二、两级存储 (two_cache.py)

### 2.1 与三级存储的区别

`two_cache.py` 没有 NPU HBM 层，只有 **DRAM 缓存 → SSD** 两级，运行时回退调用 `dlrm_s_pytorch.py`（纯 CPU/GPU）。可以看作三级存储去掉 HBM 后的简化版本。

### 2.2 存储层级

| 层级 | 介质 | 容量 | 实现 |
|------|------|------|------|
| Level 1: DRAM | CPU 内存 | `num_embeddings × dram_cache_ratio`（默认 5%） | `LRUCache` |
| Level 2: SSD | 模拟磁盘 | TB级 | `SSDStorage`（dict + 随机初始化）|

### 2.3 查找流程

```
forward(indices)
  │
  ├─ LRUCache.contains(idx)  → DRAM 命中？
  │   └─ Yes: 从缓存取，.to(device)
  │
  └─ SSDStorage.deferred_init(idx)  → SSD 冷加载
      └─ 随机初始化 + .to(device) + 回写 DRAM
```

与三级存储的关键差异：

- **无 HBM 层**：没有 `nn.Parameter`、没有梯度直接在 NPU 上更新
- **无动态迁移**：DRAM 缓存纯靠 LRU 自然淘汰，不做基于频率的主动晋升/驱逐
- **支持 offsets 聚合**：`forward` 可接收 `offsets` 参数做 EmbeddingBag 式的分段求和

### 2.4 适用场景

适合纯 CPU 时的功能验证，或作为三级存储的对照组，运行依赖 `dlrm_s_pytorch.py`。

### 2.5 访存计时

forward 内对 2 段数据通路分别计时，自动打印：

| 计时段 | 测量内容 |
|--------|---------|
| DRAM → CPU | hit发生在DRAM上的数据传输时间 |
| SSD → DRAM | 数据从SSD迁移到DRAM耗时 |

## 三、基于重用距离的存储层级预测 (reuse_distance.py)

### 3.1 解决的问题

已知一个 Embedding 的访问序列（训练或推理时的索引访问记录），如何**预测每个 Embedding 应该放在哪一级存储**，进而**预测各级访存路径的命中比例**？

这是对存储层级行为的离线建模——不依赖实际部署，仅凭访问模式就能估算出 HBM/DRAM/SSD 各自的命中率，用于架构评估和性能建模。

### 3.2 核心概念：重用距离

**重用距离（Reuse Distance）**：同一个 Embedding 两次相邻访问之间，夹了多少个**不同**的 Embedding。

```
访问序列: S = [A, B, A, B, C, B, A]

A 的重用距离: 第 1 次 A 与第 2 次 A 之间夹 {B}     → 1
             第 2 次 A 与第 3 次 A 之间夹 {B, C}  → 2
B 的重用距离: 第 1 次 B 与第 2 次 B 之间夹 {A}     → 1
             第 2 次 B 与第 3 次 B 之间夹 {C}     → 1

→ A 的重用距离 [1, 2]（均值 1.5），B 的重用距离 [1, 1]（均值 1）
```

- 重用距离**小** → 频繁被访问 → 热数据 → 预测放 HBM
- 重用距离**中** → 偶尔被访问 → 温数据 → 预测放 DRAM
- 重用距离**大 / 只访问一次** → 冷数据 → 预测放 SSD

### 3.3 计算方式：哈希表 last + 树状数组 fw（O(N log N)）

维护两个结构：

- `last[e]`：元素 e 上一次出现的时间戳（哈希表）
- `fw`：树状数组（Fenwick Tree），位置 t 为 1 当且仅当 t 是某个元素当前「最后一次出现」的时间戳

再次访问元素 e 时：

```
RD(e) = fw.prefix(t) - fw.prefix(last[e]+1)
      = (last[e], t) 区间内仍活跃的不同元素个数
```

随后**清除** `last[e]` 处的旧标记（置 0），在 t 处**打新标记**（置 1），更新 `last[e] = t`。每个元素算出所有重用距离后取平均值 d̄(e)。

### 3.4 两种层级分配模式

得到 d̄(e) 后，结合存储容量配置预测每行放哪一级：

- **阈值模式**：某级缓存能装下 d 个向量，`d̄(e) ≤ d` 即命中该层（`≤ d_hbm → HBM`、`≤ d_dram → DRAM`、其余 SSD）。速度快，但可能出现存放行数超过容量的情况。
- **容量模式**：按 d̄(e) 升序排序，依次装满 HBM（top-`hbm_rows`）、DRAM（再 `dram_rows`）、SSD（其余）。较慢，但假设各级尽可能放满。

两种模式最后都回放访问序列，统计各级命中比例（h_HBM / h_DRAM / h_SSD）。

## 四、访存时间模型 T = α×n + DataSize/BW (memory_model.py)

### 4.1 模型形式与物理含义

各段数据搬移耗时统一用「固定开销 + 带宽」刻画：

```
T = α × n + DataSize / BW

  α        每次操作的固定延时（内核启动、DMA 建立、队列调度）
  n        传输操作发生的次数
  DataSize 搬移的总字节数
  BW       有效带宽
```

### 4.2 四级通路

单次推理中 Embedding 查询触发的四段数据搬移：

| 通路 | 方向 | n 来源 |
|------|------|--------|
| HBM → NPU | 片上 gather | r_HBM · K |
| DRAM → CPU | PCIe 主机→设备 | r_DRAM · K |
| SSD → DRAM | NVMe 读 | r_SSD · K |
| DRAM → HBM | 迁移写 | N_HBM · η |

总访存延迟为四段之和：T_total = Σ T_i。

## 五、迁移与写回的时间建模

### 5.1 迁移（measure_migration_bw.py）

三条迁移链路，各自拟合 T = α*n+ S/BW（用大块拷贝扫描多档大小，斜率 = 1/BW，截距 = α）：

| 链路 | 方向 | 行为 |
|------|------|------|
| HBM→DRAM | device→host (PCIe) | 淘汰 |
| DRAM→HBM | host→device (PCIe) | 晋升 |
| SSD→DRAM | NVMe 随机读 | 晋升 |

SSD 段用 fio 随机读（QD=1 `--direct=1`）标定，绕开 OS 页缓存。

### 5.2 写回（update_model.py）

训练时的梯度更新写回，自上而下两条链路：

| 链路 | 方向 | 行为 |
|------|------|------|
| NPU→DRAM | device→host (PCIe) | 温行写回 |
| DRAM→SSD | NVMe 随机写 | 脏行批量刷回 |

NPU→HBM 原地 read-modify-write 在片上完成，零跨层流量，不建模。写回通常**批量**执行，故模型为 T = α·n_batches + DataSize/BW（α 按拷贝批次计，不按行计）；n 为传输操作发生的次数（同一行被 batch 命中多次也只写回一次）。SSD 写 ≪ SSD 读，需用 fio `randwrite` 单独标定，是训练场景的主要开销。
